Offline save hangs forever (no feedback)

Critical
File: frontend/app.js — saveInvoice, saveCustomer, saveReceipt, etc.

Offline অবস্থায় Save চাপলে UI hang হয়ে থাকে, কারণ Firestore write promise সার্ভার confirm না করা পর্যন্ত resolve হয় না। Local-এ instant সেভ + background auto-sync চাই।

This app uses Firebase Firestore with persistentLocalCache for offline-first
behavior (see frontend/boot.js where initializeFirestore is configured with
persistentLocalCache). The problem: throughout frontend/app.js, save functions
like saveInvoice(), saveCustomer(), saveReceipt(), saveCheque(), saveCreditNote(),
saveDebitNote(), and similar functions use `await addDoc(...)` / `await
updateDoc(...)` directly and update the UI (toast, closing modal, etc.) only
after that await resolves.

Per Firestore Web SDK behavior, these write promises only resolve once the
backend acknowledges the write — they do NOT resolve just because the write was
applied to the local cache. This means when the user is offline, clicking Save
will hang indefinitely with no feedback, even though the data has already been
written to the local cache and would show up correctly via onSnapshot listeners.

Fix this across all save functions in frontend/app.js:
1. Do not block the UI (toast/close modal/spinner) on the write promise
   resolving. Instead, fire the write, and immediately show optimistic UI
   feedback (e.g. "Saved — will sync when online" if offline, or "Saved" if
   online), then let the write promise resolve/reject in the background.
2. Use `navigator.onLine` (or the existing online/offline detection if any
   exists in the codebase) to decide which toast message to show ("সেভ হয়েছে"
   vs "সেভ হয়েছে — অনলাইনে এলে sync হবে").
3. Still attach a `.catch()` to each write promise so that if the write
   eventually fails for a reason OTHER than being offline (e.g. permission
   denied, quota exceeded — see the "quota exceeded" fix), the user gets
   notified later via a toast/banner, since by then the modal may already be
   closed.
4. Do not change the actual document shape/fields being written — only change
   how the UI reacts to the write promise timing.
5. Apply this consistently across all similar save/update functions in
   frontend/app.js, not just saveInvoice.

Test the change by simulating offline (DevTools > Network > Offline), creating
an invoice, and confirming the UI responds instantly instead of hanging, and
that the invoice appears in the list immediately (from local cache).

Friendly "storage full" (quota exceeded) error message

UX
File: frontend/app.js + new shared helper

Firebase free plan-এর 1GB storage শেষ হলে যেন স্পষ্ট Bengali মেসেজ দেখায়, generic error না।

Firebase Firestore's free Spark plan has a 1 GiB total storage cap that does not
reset over time (unlike the daily read/write quotas). Once a shop's Firestore
project exceeds this, new writes (addDoc/updateDoc/setDoc) will be rejected by
the server with a Firestore error whose `code` is "resource-exhausted".

Currently, save functions in frontend/app.js do not distinguish this from any
other error — the user just sees a generic failure or may not see anything
obvious at all (see the offline-save fix for related context).

1. Add a shared helper function, e.g. `friendlyFirestoreError(e)` (put it in
   frontend/app.js near other shared utilities, or in a small new file
   frontend/firestore-errors.js if that fits the project's file organization
   better), that inspects `e.code` and returns a clear Bengali message for
   known cases:
   - "resource-exhausted" → "Firebase স্টোরেজ (1GB ফ্রি লিমিট) শেষ হয়ে গেছে। নতুন ডেটা সেভ হচ্ছে না। Firebase Console-এ গিয়ে Blaze প্ল্যানে upgrade করুন অথবা পুরনো ডেটা মুছে জায়গা খালি করুন।"
   - "permission-denied" → existing/appropriate message
   - default → the raw e.message as fallback

2. Wire this helper into the `.catch()` handlers for all save functions, so
   that when a write ultimately fails (including due to quota), the user sees
   this specific, actionable message via the existing toast() function
   instead of a generic error.

3. Do not change any Firestore rules or data model — this is purely about
   catching and explaining a specific error condition to the user.

Horizontal page overflow on mobile (root cause)

Critical
File: frontend/tracker.css (.topbar), frontend/index.html

Dashboard-এ ডানে-বামে swipe করতে হচ্ছে কারণ topbar-এর ভেতর (back+menu+search+theme+notif+Logout+avatar+name) সব একসাথে গাদাগাদি করে ফিট করানোর চেষ্টা হচ্ছে, wrap/shrink হচ্ছে না, আর body-তে overflow-x:hidden কোথাও নাই — তাই পুরো page চওড়া হয়ে scrollable হয়ে যাচ্ছে।

The mobile dashboard requires horizontal swiping to see all content — this is a
page-wide horizontal overflow bug, not a single-element issue.

Root cause: in frontend/index.html, the 
 contains many
items in a flex row (mobile-back button, mobile-menu button, search input,
theme-toggle button, notif button, logoutBtn button, avatar div, and a
userName/userRole text block). In frontend/tracker.css, `.topbar{display:flex;
justify-content:space-between}` has no `flex-wrap`, and none of its children
have `min-width:0` or text-overflow/ellipsis handling, so on narrow mobile
screens their combined content width exceeds the viewport. Since there is no
`overflow-x:hidden` anywhere on body/html/.app/.main in the whole stylesheet,
the browser widens the entire scrollable page to fit that one overflowing row
instead of clipping or wrapping it — causing the whole dashboard to need
horizontal scrolling.

Fix in two parts:

1. Defensive fix (do this regardless of other changes): add `overflow-x:hidden`
   to `html, body` in frontend/tracker.css, and confirm `.app` and `.main` also
   don't allow horizontal overflow, so no future layout mistake can cause the
   whole page to become horizontally scrollable again.

2. Root fix: this project already has a separate header-redesign task planned
   (removing avatar/userName/userRole/logoutBtn from the topbar entirely and
   moving Logout into the sidebar footer, adding a prominent shop name and
   reorganizing search/notif/theme-toggle). Apply that redesign — once the
   topbar has far fewer competing elements, it will naturally fit mobile width.
   If that redesign work is being done in a separate prompt/session, at minimum
   also do this here: wrap the topbar's `.top-actions` children in a flex
   container with `flex-wrap:wrap` and `justify-content:flex-end` for mobile
   (@media max-width:760px), and give `#userName`/`#userRole`'s parent a
   `max-width` with `text-overflow:ellipsis; white-space:nowrap; overflow:hidden`
   so a long owner name can never force extra width.

Test on a 375-390px wide viewport (Chrome DevTools mobile emulation) that the
page never needs horizontal scrolling, on both the Dashboard and at least two
other pages (e.g. Invoices, Customers).
